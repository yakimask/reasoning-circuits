# 推論回路の同定 — Reasoning Circuits

Transformer の中で「知識」と混ざっている **推論の部分だけを特定して削り出す** ための実験ノートブックです。

対象モデルは `Qwen2.5-0.5B-Instruct`。分析には [TransformerLens](https://github.com/TransformerLensOrg/TransformerLens) を使い、
図や計算はできる限り **公式デモのコードをそのまま流用** しています（各セルに `[公式流用] <ファイル名> cell <番号>` と出典を明記）。

---

## 何を測っているか

1つの問題につき、モデル内部の **全成分がその答えにどれだけ寄与したか** を数値化します。

| 成分 | 個数 | 取得方法 |
|---|---|---|
| 注意ヘッドの出力 | 24層 × 14 = 336 | 順伝播1回 |
| FFN ニューロン | 24層 × 4,864 = **116,736** | 順伝播1回 |
| Q（query） | 24層 × 14 = 336 | 勾配 |
| K（key） | 24層 × 2 = 48 | 勾配 |
| V（value） | 24層 × 2 = 48 | 勾配 |
| Z（ヘッド出力前） | 24層 × 14 = 336 | 勾配 |

合計 **約117,840成分 / 1問**。値は「正解ロジット − 不正解ロジット」への寄与で、正なら正解を後押し、負なら逆方向に押しています。

> **注意**: Qwen2.5 は GQA（グループ化クエリ注意）を使うため、Q は14個ですが **K と V は2個** しかありません（7ヘッドで1組を共有）。

## 設計の根拠

### なぜ領域を1つ（推移的推論）に絞ったか

推論の共通項は **「関係を処理すること」** です（Halford の関係複雑性理論、Spearman の g 因子の定義）。
領域が違っても中身は関係処理なので、動かすべき変数は **関係の数** であって領域ではありません。
領域を増やすのは「出た回路が表面に依存しない」ことの確認用で、後工程です。

関係処理の容量を測る正典的課題は **推移的推論** と **ラテン方格課題** の2つだけで、後者は図形なのでテキストでは使えません。
また3項の推移推論は ternary（関係3個）であり、**二項関係の連鎖に還元できない** ことが知られています。

### 関係の数だけを動かす

| 条件 | 内容 | 関係の数 |
|---|---|---|
| `rel0` | `Ann is tall. Bob is short.` | 単項述語（統合不要） |
| `rel1` | `A > B` | 2項 |
| `rel2` | `A > B > C` | 3項 |
| `rel3` | `A > B > C > D` | 4項（人間の処理限界） |
| `rel4` | `A > B > C > D > E` | 5項 |

### なぜ質問を固定して前提を壊すか

パッチングが追うのは「clean と corrupted の違いを運ぶ部品」です。
**質問語を反転させると（tallest ↔ shortest）、順序を組み立てる作業が両方の実行で同一になり、差分から消えます。**
それでは読み出しの回路しか追えません。**前提を壊せば順序そのものが変わる** ので、差分に統合の作業が乗ります。

```
clean     : Bob > Cid.  Ann > Bob.  The tallest one is  → Ann
corrupted : Bob > Cid.  Dan > Bob.  The tallest one is  → Dan
                        ↑1語だけ違う
```

### なぜ前提の順番をランダムにするか

降順に並べると「最大＝最初の名前 / 最小＝最後の名前」と位置で決まり、統合せずに位置だけで正解できてしまいます。
順番を崩すとこの戦略が通りません。実測でも **「直近の名前を答えた率」が全条件で 0%** になりました。

## セットアップ

VS Code から Colab ランタイムに接続して使う想定です（Google 公式の [Colab 拡張](https://marketplace.visualstudio.com/items?itemName=Google.colab)）。
ノートブックをローカルに置いたまま、実行だけ Colab の GPU で行えます。

### 必ず踏む罠が3つあります

**1. 図が無言で出ない**

公式デモは Colab を検出すると plotly のレンダラを `"colab"` に設定しますが、これは Colab のウェブ画面専用です。
VS Code では **エラーも出さずに図が一切描画されません**。STEP 1 で `notebook_connected` に上書きしています。
STEP 2 が描画テストなので、まずここで確認してください。

**2. カーネル再起動でゾンビが残る**

VS Code の「カーネル再起動」は Colab 側の古いプロセスを殺しません。
再起動を繰り返すと GPU を掴んだままのプロセスが積み上がり、OOM になります。
STEP 1 の `wipe_memory()` が他プロセスを終了させ、IPython の出力履歴（`Out`）も消します。

**3. タブを開いたままだと編集が消える**

VS Code は外部からのファイル変更を自動では取り込まず、保存時に上書きします。
ノートブックを書き換えるときは **タブを閉じてから** 行ってください。

## STEP 一覧

| STEP | 内容 | コスト | 依存 |
|---|---|---|---|
| 1 | 環境・モデル読み込み・メモリ掃除 | 数分（初回DL） | — |
| 2 | 描画テスト | 一瞬 | 1 |
| 3 | **問題の生成**（rel0〜rel4、約210問） | 一瞬 | 1 |
| 4 | 検査 → 展開 → スクリーニング | 数秒 | 1, 3 |
| 5 | 指標の定義（正規化ロジット差） | 一瞬 | 4 |
| 6 | パッチング図 8枚（denoising = 十分性） | **重い** | 5 |
| 7 | パッチング図 8枚（noising = 必要性） | **重い** | 5 |
| 8 | 十分性 vs 必要性 の突き合わせ | 一瞬 | 6, 7 |
| 9 | DLA（層別・ヘッド別）+ 既知ヘッド型の検出 | 数秒 | 4 |
| 10 | 条件をまたいだ交差の集計 | 数秒 | 6, 7 |
| 11 | アブレーション（1個削って前後比較） | 数秒 | 9 |
| 12 | アブレーション（複数まとめて削る） | 数秒 | 9 |
| 15 | **1問 = 1ファイルで全成分を書き出す** | 全問で15〜40分 | 1, 3 |

### 速い方法と遅い方法の違い

```
STEP 15   勾配による1次近似        … 速い（順伝播2回 + 逆伝播1回）。候補の絞り込み用
STEP 6/7  実際に活性を差し替える    … 遅い（約8,000回の順伝播）。答え合わせ用
```

**両方必要です。** 勾配による近似は外すことがあり（"When Attribution Patching Lies" という研究があります）、
**最終的な主張は本物のパッチングで裏を取る** べきというのが現在の理解です。

ただし総当たりする必要はありません。**STEP 15 で候補を数十個に絞ってから STEP 6/7 をかける** のが現実的な順序です。

## やりたいこと別の使い方

### 「どの層・どのヘッドが反応したか」をざっと見たい

**STEP 1 → 3 → 4 → 9**

順伝播1回で終わります。層ごとの Attn / MLP の寄与、24層×14ヘッドのヒートマップ、
候補ヘッドが既知の型（前トークン・重複トークン・誘導ヘッド）に当たるかの判定まで出ます。

> 既知の型に当たったら要注意です。推論回路ではなく **コピー機構** を見ている可能性があります。

### 1問ごとの全成分データが欲しい（CSV）

**STEP 1 → 3 → 15**

`RUN_ALL = True` にすると全問ぶん、`/content/out/q001_rel0_000.csv` の形式で1問1ファイルを書き出します。
既にファイルがある問題は飛ばすので、途中で落ちても再実行すれば続きから再開します。

1ファイル約6MB × 約210問 = 約1.3GB。**ランタイムが切れると `/content/` は消えるので、終わったら Drive に退避してください。**

### ヘッドの役割（運び屋か案内役か）を知りたい

**STEP 15** の出力のうち `kind` が `q` / `k` / `v` の行を見ます。

```
V が大きい → 情報を運んでいる（運び屋）
Q が大きい → どこを見るかを決めている（案内役）
K が大きい → 見つけられる側の情報
```

### 因果を確かめたい（近似ではなく実測）

**STEP 1 → 3 → 4 → 5 → 6 → 7 → 8**

重いので、STEP 15 で候補を絞ってから実行してください。

- **denoising**（corrupted を走らせ clean を差す）… その部品「だけで」答えが決まるか＝**十分性**
- **noising**（clean を走らせ corrupted を差す）… その部品を壊すと崩れるか＝**必要性**

**この2つは非対称で、一方が他方を含意しません。** AND 型の回路は denoising でしか見えず、OR 型は noising でしか見えません。

### 削って確かめたい

**STEP 11 → 12**

`HEADS_TO_ABLATE` に `(層, ヘッド)` を並べます。

> **自己修復（Hydra効果）に注意。** 削っても性能が落ちないことがあります。予備の部品が肩代わりするためです。
> STEP 11 は削除前後のヘッド別寄与を散布図で比較します。**寄与が増えたヘッドがあれば、それが予備部品** です。
> その場合は「不要」ではなく、**予備も含めてまとめて削る** 必要があります。

## 実測されたこと（Qwen2.5-0.5B-Instruct）

### 関係の数と正答率

```
条件    clean   corrupted   直近を答えた率
rel0    68.0%     64.0%        0.0%
rel1    95.2%     88.1%        0.0%
rel2    79.1%     88.4%        0.0%
rel3    57.5%     70.0%        0.0%
rel4    27.0%     37.8%        0.0%
```

関係が4個（rel3）を超えると崩れます。**Halford の理論が予測する処理容量の限界と一致** します。
`rel3` / `rel4` は正答率が低いため回路の追跡には使えませんが、**限界の記述としてはそのまま使えます**。

### どこが効いているか

2つの独立した方法が同じ場所を指しました。

| | 順伝播（DLA） | 勾配（attribution） | 一貫性 |
|---|---|---|---|
| **L20 ヘッド7** | +1.112 | `L20Z7` +0.055 | **100%** |
| **L20 ヘッド12** | +1.269 | `L20Z12` +0.050 | **100%** |
| L20 KV組1 | — | `L20V1` +0.077（最大） | **100%** |
| L23 ヘッド12 | −0.761 | `L23Z12` −0.026 | **0%**（一貫して負） |

- **主役は注意層で、MLP は脇役**。最上位のニューロン（L22N1222 = +0.401）はヘッドに遠く及びません
- **V が首位** = 重要なヘッドは「情報を運ぶ役」。これは既知の傾向と一致します
- **単独で支配的な部品は存在しません**。最大でも全体の8%弱で、**多数に分散** しています

### 一貫性で真贋が割れます

```
L20H12  平均 +1.269  一貫性 100%   ← 本物
L23H13  平均 +1.301  一貫性  62%   ← 平均は最大だが不安定
```

**平均だけで選ぶと間違ったヘッドを削ります。** 一貫性（何割の問題で正の寄与だったか）を必ず併記してください。

## 既知の限界

- **最小性は保証されません。** 得られるのは「十分な部品集合」であって最小回路ではありません
- **分布外は主張できません。** テストしたテンプレート分布での結論です
- **多義性。** 1つの部品が複数の機能を担いうるため、部品単位では推論だけを分離しきれない場合があります
  → その場合は **辺（component 間の接続）単位** の分析が必要です
- **領域は推移的推論のみ。** 汎用性は関係数の軸から主張していますが、別領域での確認は未実施です
